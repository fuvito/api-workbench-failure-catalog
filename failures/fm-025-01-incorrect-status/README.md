# fm-025-01 — Incorrect HTTP Status and Business-Error Semantics

> Full catalog entry: https://clrsig.com/failures/fm-025/

**Difficulty:** Easy
**Detected by:** `clrsig run` status assertion
**Port:** 19025

**Primary failure mode:** [FM-025 — Incorrect HTTP Status and Business-Error Semantics](https://clrsig.com/failures/fm-025/)  

## What this failure is

The server returns `200 OK` for every request — including requests for resources that do not exist. The response body signals the error correctly (`{"error":"not found","code":"PRODUCT_NOT_FOUND"}`), but the HTTP status says success.

This pattern appears when developers route all error handling through a uniform `200` response to avoid triggering HTTP-status-based alerts. The result: HTTP clients, proxies, load balancers, and monitoring dashboards all see success. The API consumer must parse the body of every response to know whether the call actually worked.

## Prerequisites

- **Go 1.22+** — verify with `go version`
- **clrsig** — install from [clrsig.com/docs/install](https://clrsig.com/docs/install/)

## Reproduce it

Run from the **repo root**:

```bash
go run failures/fm-025-incorrect-status/broken/main.go &
clrsig run failures/fm-025-incorrect-status/scenarios/detect.yaml \
  --env failures/fm-025-incorrect-status/environments/local.yaml
```

Expected: **clrsig exits 1** — the step "missing product must return 404" received `200 OK`.

Expected output *(illustrative — run the command to see current output)*:
```
(regenerated by CI — see .github/workflows/update-outputs.yml)
```

Stop the server before running the fixed version:

```bash
# macOS / Linux
pkill -f 'broken/main.go'

# Windows (PowerShell)
Stop-Process -Id (Get-NetTCPConnection -LocalPort 19025).OwningProcess
```

## Why clrsig catches it

The scenario (`scenarios/detect.yaml`) sends `GET /products/9999` and asserts:

```yaml
assertions:
  - type: status
    expected: 404
```

The broken server returns `200`, so the assertion fails and clrsig exits 1.

The declared spec (`openapi.yaml`) lists `404` as a valid response for missing products. This is the contract the scenario enforces.

See [status assertions](https://clrsig.com/docs/format-spec/) in the Clear Signal format spec.

## Fix

```bash
go run failures/fm-025-incorrect-status/fixed/main.go &
clrsig run failures/fm-025-incorrect-status/scenarios/detect.yaml \
  --env failures/fm-025-incorrect-status/environments/local.yaml
# exits 0
```

**What changed:** `broken/main.go` — `http.StatusOK` → `http.StatusNotFound` for the not-found branch. One field, full contract compliance.

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` with your API's address:

```yaml
baseUrl: https://your-api.example.com
```

Update `scenarios/detect.yaml` to target your endpoint:

```yaml
steps:
  - name: missing resource returns 404
    request:
      method: GET
      path: /your-resource/nonexistent-id
    assertions:
      - type: status
        expected: 404
```

The scenario is portable — copy the two files into your workspace and point them at any HTTP API.

## In the wild

This failure mode appears in:

- **Internal services** that swallow errors in middleware and return a uniform `200` envelope to avoid triggering HTTP-status-based alert rules
- **Framework migrations** where the original framework treated HTTP status as a transport concern separate from application logic — porting the app kept the error body structure but dropped the correct status codes
- **Teams monitoring at the wrong layer** — tracking `response.error` fields rather than HTTP status; dashboards stay green, but downstream clients that test `response.ok` (true for 2xx only) silently swallow every failure
