# fm-004-01 — Renamed or Removed Response Fields

> Full catalog entry: https://clrsig.com/failures/fm-004/

**Difficulty:** Medium
**Detected by:** `clrsig diff` v1 vs v2
**Port:** none (diff-based — no server required)

**Primary failure mode:** [FM-004 — Renamed or Removed Response Fields](https://clrsig.com/failures/fm-004/)  

## What this failure is

Between v1 and v2 of the User API, a developer made two breaking changes without a deprecation period:

1. **`full_name` renamed to `name`** — consumers reading `response.full_name` now get `undefined`
2. **`phone` removed entirely** — consumers reading `response.phone` now get `undefined`

Both fields were `required` in v1. Renaming a required field is indistinguishable from removing it and adding a new one — it is always breaking. Any consumer deployed against v1 silently breaks the moment v2 ships.

This sub-project is diff-based: there are no servers to run. The two spec files are the demonstration. `clrsig diff --breaking-only` exits 1 when it detects the violations.

## Why clrsig catches it

`clrsig diff` compares the two spec files and flags any change that removes or modifies a field consumers depend on. Breaking changes in `--breaking-only` mode:

| Change | Why it's breaking |
|---|---|
| `full_name` removed from `required` | Consumers that read `full_name` get `undefined` |
| `full_name` absent from properties | Same — a remove followed by a differently-named add is still a remove |
| `phone` removed from `required` | Consumers that read `phone` get `undefined` |
| `phone` absent from properties | Same |

The two spec files are the complete reproduction:
- `v1/openapi.yaml` — the contract consumers were coded against
- `v2/openapi.yaml` — the version that introduced the breaking changes

## Fix

There is no server to fix — the fix is to not introduce the breaking changes in the first place, or to follow a non-breaking migration path:

**Non-breaking rename (v2 done correctly):**
```yaml
# v2/openapi.yaml — add the new name, keep the old, mark old as deprecated
User:
  required: [id, full_name, name, email, phone]
  properties:
    full_name:
      type: string
      deprecated: true       # still present — existing consumers keep working
      description: "Deprecated: use 'name' instead"
    name:
      type: string            # new field added alongside the old one
    phone:
      type: string            # still present — was not removed
```

Consumers migrate to `name` on their own schedule. Remove `full_name` only in v3, after a deprecation window.

**Running the non-breaking diff:**
```bash
# With the corrected v2 above, clrsig diff exits 0:
clrsig diff failures/fm-004-01-renamed-removed-field/v1/openapi.yaml \
            path/to/corrected-v2.yaml \
            --breaking-only
# exits 0 — no breaking changes
```

## In the wild

Renamed or removed fields appear when:

- **Domain model refactors** standardize naming conventions (`full_name` → `name`, `is_active` → `active`) across a service without a deprecation window
- **Data minimization** — a team removes fields to reduce payload size or stop returning PII (`phone`, `address`), without checking who reads those fields
- **Microservice decomposition** — a field moves to a new service's response; the original service drops it without realizing consumers relied on it
- **"Clean up" migrations** — a developer removes fields marked `deprecated` in comments but never formally deprecated in the spec or communicated to consumers
