# fm-005-01 — Incorrect Optional, Nullable, and Required Field Behavior

> Full catalog entry: https://clrsig.com/failures/fm-005/

**Difficulty:** Easy
**Detected by:** `clrsig run` schema assertion
**Port:** 19005

**Primary failure mode:** [FM-005 — Incorrect Optional, Nullable, and Required Field Behavior](https://clrsig.com/failures/fm-005/)  

## What this failure is

The spec declares `email` as a `required`, non-nullable `string` field. The broken server uses a nullable Go pointer (`*string`) for the field — users who registered via OAuth have no email stored, so the server emits `"email": null`.

A `null` value fails the `type: string` assertion because OpenAPI 3.0's `type: string` does not include null unless `nullable: true` is explicitly set. The contract promises a string; consumer code that calls `.toLowerCase()` or passes the value to a function expecting a string will crash or silently corrupt data.

## Why clrsig catches it

The scenario sends requests for two users and asserts the same schema on `$.email`:

```yaml
assertions:
  - type: schema
    path: $.email
    schema:
      type: string
```

User 1 (`/users/1`) passes — `email` is `"alice@example.com"`. User 2 (`/users/2`) fails — `email` is `null`. clrsig exits 1 on the first failing step.

The declared spec (`openapi.yaml`) marks `email` as `required` with `type: string` and no `nullable: true`. A `null` value is not a valid `string` in OpenAPI 3.0.

See [schema assertions](https://clrsig.com/docs/format-spec/) in the Clear Signal format spec.

## Fix

```bash
go run failures/fm-005-nullable-required/fixed/main.go &
clrsig run failures/fm-005-nullable-required/scenarios/detect.yaml \
  --env failures/fm-005-nullable-required/environments/local.yaml
# exits 0
```

**What changed:** `broken/main.go` — `Email *string` → `Email string`. Users registered without an email now receive an empty string `""`, which satisfies `type: string`.

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` with your API's address:

```yaml
baseUrl: https://your-api.example.com
```

Adjust the step paths and field names in `scenarios/detect.yaml`:

```yaml
steps:
  - name: required field must not be null
    request:
      method: GET
      path: /your-resource/known-edge-case-id
    assertions:
      - type: schema
        path: $.your_required_field
        schema:
          type: string   # or integer, boolean, array, object
```

The edge-case ID in the path is the key: target a resource you know the server might return a null or missing field for — a user with no profile photo, an order with no shipping address, a product with no description.

## In the wild

This failure mode appears in:

- **OAuth / SSO integrations** — users log in via a third-party provider that does not share an email address; the backend stores `null` in the email column and serializes it as-is
- **Legacy schema migrations** — a column is added as optional in the database but declared required in a newer version of the OpenAPI spec; existing rows have `NULL` in the database
- **Partial-update endpoints** — a `PATCH` handler returns the patched resource, but fields not included in the patch are serialized as `null` instead of their current values
- **Go pointer gotcha** — developers use `*string` throughout the model layer for optional database fields, then forget to change the type for fields the spec marks non-nullable
