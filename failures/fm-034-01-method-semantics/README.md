# fm-034-01 — HTTP Method and Operation Semantics Failures

> Full catalog entry: https://clrsig.com/failures/fm-034/

**Difficulty:** Medium
**Detected by:** `clrsig run` + `specFile:` schema assertions
**Port:** 19034

**Primary failure mode:** [FM-034 — HTTP Method and Operation Semantics Failures](https://clrsig.com/failures/fm-034/)  

## What this failure is

The server implements the right endpoints but uses the wrong HTTP status codes for each method. Two violations are present:

1. **`POST /articles` returns `200 OK`** — the HTTP spec says a successful resource creation should return `201 Created`, and the OpenAPI spec declares only `201`. Clients that check the status code to decide whether to follow the `Location` header will never follow it; clients that assume `201` means "new resource created" will silently treat this as an unexpected state.

2. **`DELETE /articles/{id}` returns `200 OK` with a JSON body** — `DELETE` should return `204 No Content` with no body. The spec declares only `204`. Clients that assume an empty body after a successful delete will blow up trying to parse `{"deleted": true}`.

Both are syntactically valid JSON responses (or empty). Schema validation alone passes. The failure only surfaces when the response's status code is checked against what the spec actually declares.

## Why clrsig catches it

The scenario binds the spec at the top level:

```yaml
specFile: ./openapi.yaml
```

Each step's `type: schema` assertion validates the response status code against the declared responses in `openapi.yaml`. The spec declares:

- `POST /articles` → `201` only
- `DELETE /articles/{id}` → `204` only

When the broken server returns `200` for both, clrsig flags the undeclared status on each step and exits 1.

## Fix

```bash
go run failures/fm-034-method-semantics/fixed/main.go &
clrsig run failures/fm-034-method-semantics/scenarios/detect.yaml \
  --env failures/fm-034-method-semantics/environments/local.yaml
# exits 0
```

**What the demo does:**

- `POST /articles` returns `201 Created` with a `Location: /articles/{id}` header
- `DELETE /articles/{id}` returns `204 No Content` with no body

Both match the spec; all assertions pass.

**What the production fix looks like:**

```go
// POST — creation returns 201 + Location
w.Header().Set("Location", fmt.Sprintf("/articles/%d", article.ID))
w.WriteHeader(http.StatusCreated)
json.NewEncoder(w).Encode(article)

// DELETE — successful deletion is silent: 204, no body
w.WriteHeader(http.StatusNoContent)
```

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` and add a step for each mutating endpoint:

```yaml
specFile: ./your-api.yaml
steps:
  - name: POST must return 201
    request:
      method: POST
      path: /resources
      body:
        name: "test"
    assertions:
      - type: schema

  - name: DELETE must return 204
    request:
      method: DELETE
      path: /resources/1
    assertions:
      - type: schema
```

If clrsig exits 1, the endpoint is returning an undeclared status code — either update the implementation or add the status to the spec.

## In the wild

Wrong status codes for HTTP methods appear when:

- **Framework defaults** — a web framework scaffolds a handler returning `200` for every route; the developer fills in the logic but doesn't change the status code for create or delete routes
- **Generic response helpers** — a shared `respond(w, data)` utility always writes `200`; the caller never overrides it for `POST` or `DELETE`
- **Copy-paste from a GET handler** — a developer clones a GET handler to build a DELETE handler, keeps the `200` from the original, and ships it
- **Spec written after the fact** — the implementation ships first with `200` everywhere; a spec is generated from the implementation but then corrected to use `201`/`204`; the implementation is never updated to match
- **Proxy or gateway normalization** — an API gateway rewrites all `201`/`204` responses to `200` for uniformity (seen in some legacy enterprise gateways)
