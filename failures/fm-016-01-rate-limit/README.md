# fm-016-01 — Rate-Limit and Throttling Failures

> Full catalog entry: https://clrsig.com/failures/fm-016/

**Difficulty:** Medium
**Detected by:** `clrsig run` + `specFile:` schema assertions (undeclared 429)
**Port:** 19016

**Primary failure mode:** [FM-016 — Rate-Limit and Throttling Failures](https://clrsig.com/failures/fm-016/)  

## What this failure is

The server enforces a rate limit and starts returning `429 Too Many Requests` once the limit is hit — but `429` is not declared anywhere in the OpenAPI spec. Consumer code has no contract telling it throttling is possible, so it has no retry logic, no backoff, and no graceful degradation. The first throttled request is a hard crash.

This is different from "rate limiting is bad". Rate limiting is correct. The failure is that the spec doesn't declare it, so the API surface is incomplete.

## Why clrsig catches it

The scenario binds the spec at the top level:

```yaml
specFile: ./openapi.yaml
```

Each step's `type: schema` assertion validates the response — including its status code — against the declared responses in the spec. `openapi.yaml` declares `200` and `404` only. When step 3 returns `429`, clrsig flags the undeclared status and exits 1.

Steps 1 and 2 pass because they return `200`, which is declared.

## Fix

```bash
go run failures/fm-016-rate-limit/fixed/main.go &
clrsig run failures/fm-016-rate-limit/scenarios/detect.yaml \
  --env failures/fm-016-rate-limit/environments/local.yaml
# exits 0
```

**What the demo does:** raises `rateLimit` from `2` to `1000` so the scenario's 3 requests never trigger throttling. All three steps return `200`, which is declared in the spec.

**What the production fix looks like** — declare `429` in the spec with the proper headers, then update consumers to handle it:

```yaml
# openapi.yaml — add to responses for every rate-limited endpoint
"429":
  description: Rate limit exceeded
  headers:
    Retry-After:
      description: Seconds to wait before retrying
      schema:
        type: integer
  content:
    application/json:
      schema:
        $ref: "#/components/schemas/Error"
```

Consumers then implement exponential backoff:
```
if response.status == 429:
    wait(response.headers["Retry-After"])
    retry()
```

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` and add steps until you trigger the rate limit:

```yaml
specFile: ./your-api.yaml
steps:
  - name: exhaust the limit
    request:
      method: GET
      path: /your-endpoint
    assertions:
      - type: schema
  # repeat the step until you know the limit is hit
```

If clrsig exits 1 on the final step, the endpoint is returning an undeclared status — add it to the spec.

## In the wild

Undeclared rate limiting appears when:

- **A platform team adds throttling retroactively** — an API has been running without rate limits; the platform adds a gateway-level 429 for all endpoints but no one updates the OpenAPI specs
- **Third-party API wrapping** — an internal service proxies a third-party API that rate-limits; the third-party 429 is forwarded directly without being declared in the internal spec
- **Burst protection added after an incident** — after a traffic spike causes an outage, ops adds an emergency rate limit at the load balancer; the spec update is filed as a follow-up ticket and never done
- **Per-tenant limits in multi-tenant SaaS** — free-tier tenants hit a 429 that paid-tier tenants never see; the spec is written from the perspective of paid-tier behavior and omits the 429 entirely
