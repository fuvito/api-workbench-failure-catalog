# fm-018-01 — Idempotency and Duplicate-Operation Failures

> Full catalog entry: https://clrsig.com/failures/fm-018/

**Difficulty:** Hard
**Detected by:** `clrsig run` multi-step scenario (status + jsonpath assertions)
**Port:** 19018

**Primary failure mode:** [FM-018 — Idempotency and Duplicate-Operation Failures](https://clrsig.com/failures/fm-018/)  

## What this failure is

The server processes every `POST /payments` request as a new payment, regardless of whether the same `order_id` has already been submitted. When a client retries due to a network timeout, dropped connection, or load-balancer retry, it gets charged twice.

The spec declares `order_id` as the natural idempotency key: submitting the same `order_id` a second time must return the existing payment (`200 OK`), not create a new one (`201 Created`). The broken server returns `201` on every POST — the duplicate is invisible in a single request but shows up in the payment count after a retry.

This is a contract failure that only surfaces across multiple requests. A single-request assertion cannot detect it. The scenario works by submitting the same payment twice and then checking that only one payment exists.

## Scenario flow

| Step | Request | Broken | Fixed |
|------|---------|--------|-------|
| 1 | POST /payments (order-42) | 201 — payment created | 201 — payment created |
| 2 | POST /payments (order-42, retry) | 201 — **duplicate created** | 200 — existing payment returned |
| 3 | GET /payments → `$.count` | **2** — assertion fails | 1 — assertion passes |

Steps 1 and 2 both return `200`-range responses on both servers; the discriminator is step 3's count.

## Why clrsig catches it

The scenario chains three requests. Steps 1 and 2 fire the same POST body — the second simulates a client retry. Step 3 inspects the state after both requests:

```yaml
- name: "only one payment must exist"
  request:
    method: GET
    path: /payments
  assertions:
    - type: jsonpath
      path: $.count
      expected: 1
```

A count of 2 means the server processed the retry as a new operation. A count of 1 means the server recognized the duplicate and returned the existing payment.

## Fix

```bash
go run failures/fm-018-01-idempotency/fixed/main.go &
clrsig run failures/fm-018-01-idempotency/scenarios/detect.yaml \
  --env failures/fm-018-01-idempotency/environments/local.yaml
# exits 0
```

**What the demo does:** adds a lookup before inserting. If a payment with the same `order_id` already exists, it returns that payment with `200 OK` instead of creating a new one:

```go
for _, p := range payments {
    if p.OrderID == input.OrderID {
        writeJSON(w, http.StatusOK, p)
        return
    }
}
// only reaches here for new order_ids
```

**What the production fix looks like** — use a database unique constraint combined with an upsert-or-return pattern:

```sql
-- Unique constraint prevents duplicate rows at the database level
ALTER TABLE payments ADD CONSTRAINT uq_payments_order_id UNIQUE (order_id);
```

```go
// Application layer: attempt insert; if conflict, fetch and return existing
_, err := db.Exec(`
    INSERT INTO payments (order_id, amount, currency, status)
    VALUES ($1, $2, $3, 'completed')
    ON CONFLICT (order_id) DO NOTHING
`, input.OrderID, input.Amount, input.Currency)

var payment Payment
db.QueryRow(`SELECT * FROM payments WHERE order_id = $1`, input.OrderID).Scan(&payment)

status := http.StatusCreated
if err == nil && payment.ID != newID {
    status = http.StatusOK  // was a duplicate
}
writeJSON(w, status, payment)
```

Alternatively, use an `Idempotency-Key` request header (Stripe-style): the client generates a UUID per payment intent and sends it as a header. The server stores the response keyed by that UUID and replays it on repeat requests.

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` and add steps for any endpoint where duplicate execution causes harm:

```yaml
steps:
  - name: submit operation
    request:
      method: POST
      path: /your-endpoint
      body:
        external_id: "op-123"
    assertions:
      - type: status
        expected: 201

  - name: retry the same operation
    request:
      method: POST
      path: /your-endpoint
      body:
        external_id: "op-123"
    assertions:
      - type: jsonpath
        path: $.external_id
        expected: "op-123"

  - name: only one record must exist
    request:
      method: GET
      path: /your-endpoint
    assertions:
      - type: jsonpath
        path: $.count
        expected: 1
```

Any endpoint that mutates state and can be retried by a client is a candidate for this pattern.

## In the wild

Idempotency failures appear when:

- **No retry deduplication** — an API is designed assuming clients send each request exactly once; when the network layer adds automatic retries (ALB, service mesh, SDK), the server processes each attempt independently
- **Missing unique constraint** — the application code has no duplicate check and the database has no unique constraint on the natural key; every retry inserts a new row
- **Idempotency check at the wrong layer** — the check is in a background job, not in the request handler; the duplicate is created before the job runs
- **Distributed race condition** — two retries arrive at two different instances simultaneously; both pass the "does this order_id exist?" check before either commits; both insert
- **Idempotency key stored separately from the resource** — the key is recorded in a separate `idempotency_keys` table; the resource insert and the key insert are not in the same transaction; a crash between them loses the key and allows re-processing
