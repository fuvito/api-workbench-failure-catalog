# fm-003-01 — Pagination Contract Failures

> Full catalog entry: https://clrsig.com/failures/fm-003/

**Difficulty:** Hard
**Detected by:** `clrsig run` multi-step scenario (jsonpath assertions)
**Port:** 19003

**Primary failure mode:** [FM-003 — Pagination Contract Failures](https://clrsig.com/failures/fm-003/)  

## What this failure is

The server hardcodes `has_more: true` on every page response — including the last one. The JSON structure is correct, the schema is valid, all required fields are present. The failure is in the value: a client that drives pagination by checking `has_more` will loop forever after the last page, repeatedly requesting an empty items list.

This is a contract failure that only surfaces across multiple requests in sequence. A single-request schema check passes on both the broken and fixed server. It takes a multi-step scenario to expose it: request page 1, page 2, then page 3 — the final `has_more` on the last page is the assertion that separates the broken server from the fixed one.

## Data layout

The server has 5 products. With `limit=2`:

| Page | Items | Expected `has_more` |
|------|-------|---------------------|
| 1    | [1,2] | `true`              |
| 2    | [3,4] | `true`              |
| 3    | [5]   | `false`             |

The broken server returns `has_more: true` on all three pages. The scenario's first two steps pass on both servers; only the final step catches the bug.

## Why clrsig catches it

The scenario chains three requests, each checking `$.has_more` via a jsonpath assertion:

```yaml
steps:
  - name: "page 1 of 3: has_more must be true"
    request:
      method: GET
      path: /products?page=1&limit=2
    assertions:
      - type: jsonpath
        path: $.has_more
        expected: true

  - name: "page 3 of 3: has_more must be false"
    request:
      method: GET
      path: /products?page=3&limit=2
    assertions:
      - type: jsonpath
        path: $.has_more
        expected: false
```

Steps 1 and 2 pass on both servers — `has_more: true` is correct for pages with more data following. Step 3 is the discriminator: the fixed server computes `end < len(products)` (false on the last page); the broken server always returns `true`.

## Fix

```bash
go run failures/fm-003-01-pagination-contract/fixed/main.go &
clrsig run failures/fm-003-01-pagination-contract/scenarios/detect.yaml \
  --env failures/fm-003-01-pagination-contract/environments/local.yaml
# exits 0
```

**What the demo does:** replaces the hardcoded `HasMore: true` with the correct expression:

```go
// broken
HasMore: true

// fixed
HasMore: end < len(products)
```

**What the production fix looks like** — compute `has_more` from the actual data boundary, not an estimate:

```go
// After slicing the result set:
hasMore := offset+limit < totalCount

// Or with cursor pagination:
hasMore := len(items) == limit  // fetched one extra item as a lookahead
```

A common pattern is to fetch `limit+1` items and use the extra item's presence to set `has_more`, then trim the slice before returning:

```go
items, _ := db.Query("SELECT * FROM products LIMIT $1 OFFSET $2", limit+1, offset)
hasMore := len(items) > limit
if hasMore {
    items = items[:limit]
}
```

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` and add a step for the last page of your collection:

```yaml
steps:
  - name: intermediate page — has_more must be true
    request:
      method: GET
      path: /your-resource?page=1&per_page=10
    assertions:
      - type: jsonpath
        path: $.has_more
        expected: true

  - name: last page — has_more must be false
    request:
      method: GET
      path: /your-resource?page=LAST_PAGE&per_page=10
    assertions:
      - type: jsonpath
        path: $.has_more
        expected: false
```

Replace `LAST_PAGE` with the actual last page number for your dataset. If you don't know it, check the `total` and `limit` fields from the first response to compute it.

## In the wild

Pagination contract failures appear when:

- **Copy-paste from a non-final page** — a developer tests the endpoint mid-dataset where there's always a next page; `has_more: true` is hardcoded because it was always true during development
- **Off-by-one in the boundary check** — `has_more` is computed as `page * limit < total` instead of `(page - 1) * limit + len(items) < total`; for even-divisor cases it returns `true` when the last page is exactly full
- **Cursor pagination left in draft state** — a cursor-based API returns a `next_cursor` token even when the cursor points to an empty result set; consumers assume a non-null cursor means more data exists
- **Cached pagination metadata** — `total` is cached at query time and not invalidated when records are deleted; `has_more` is derived from a stale `total` and reports pages that no longer exist
- **Database count query skipped for performance** — to avoid a `COUNT(*)`, the developer always returns `has_more: true` and relies on the client to stop when `items` is empty; the client does not implement that check
