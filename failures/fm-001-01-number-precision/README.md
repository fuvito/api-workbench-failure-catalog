# fm-001-01 — Currency, Number, and Precision Formatting Failures

> Full catalog entry: https://clrsig.com/failures/fm-001/

**Difficulty:** Easy
**Detected by:** `clrsig run` schema assertion
**Port:** 19001

**Primary failure mode:** [FM-001 — Currency, Number, and Precision Formatting Failures](https://clrsig.com/failures/fm-001/)  

## What this failure is

The server returns monetary amounts (`subtotal`, `tax`, `total`) as JSON strings — `"24.00"` — instead of JSON numbers — `24.00`. The OpenAPI spec declares these fields as `type: number`, so a schema-aware validator sees a type mismatch immediately.

This pattern appears when:
- The backend stores amounts in string columns (e.g. `DECIMAL` columns read as strings by some database drivers)
- A Java/Kotlin `BigDecimal` or Python `Decimal` is serialized to its `.toString()` representation
- The team "avoids floating-point precision issues" by using strings — without updating the spec or notifying consumers

The consequence: consumer code that does arithmetic on the values (`total + tax`) breaks or produces wrong results in languages that do not silently coerce strings to numbers.

## Why clrsig catches it

The scenario (`scenarios/detect.yaml`) sends `GET /invoices/1` and asserts the JSON type of each monetary field:

```yaml
assertions:
  - type: schema
    path: $.subtotal
    schema:
      type: number
```

The broken server responds with `"subtotal": "20.00"` (a string). The schema assertion fails, and clrsig exits 1.

The declared spec (`openapi.yaml`) marks all three fields as `type: number, format: float`. This is the contract the scenario enforces.

See [schema assertions](https://clrsig.com/docs/format-spec/) in the Clear Signal format spec.

## Fix

```bash
go run failures/fm-001-number-precision/fixed/main.go &
clrsig run failures/fm-001-number-precision/scenarios/detect.yaml \
  --env failures/fm-001-number-precision/environments/local.yaml
# exits 0
```

**What changed:** `broken/main.go` — `Subtotal`, `Tax`, `Total` fields changed from `string` to `float64` in the `Invoice` struct. The JSON encoder now emits `24.00` instead of `"24.00"`.

## Adapt this to your API

Replace `baseUrl` in `environments/local.yaml` with your API's address:

```yaml
baseUrl: https://your-api.example.com
```

Update `scenarios/detect.yaml` to target your endpoint and numeric fields:

```yaml
steps:
  - name: amount fields must be numbers
    request:
      method: GET
      path: /your-endpoint
    assertions:
      - type: schema
        path: $.amount
        schema:
          type: number
```

You can add as many `type: schema` assertions as there are numeric fields to enforce.

## In the wild

This failure appears in:

- **Database-backed APIs** where ORM/driver maps `DECIMAL` or `NUMERIC` columns to strings — the amount is accurate but the type is wrong
- **Precision-anxious teams** that return all monetary values as strings to dodge IEEE 754 rounding, without coordinating the type change with consumers or updating the spec
- **Microservice boundaries** where a payment service returns amounts as `BigDecimal.toString()` and a downstream service tries to do arithmetic, only to discover it is summing strings
- **Serializer defaults** — some frameworks (older Spring Boot, some PHP serializers) quote numeric types when the backing field is typed as `Object` or `mixed`
