# fm-044-01 — Sensitive Data Exposure in API Responses

> Full catalog entry: https://clrsig.com/failures/fm-044/

**Difficulty:** Medium
**Detected by:** `clrsig run` schema (`additionalProperties: false`)
**Port:** 19044

**Primary failure mode:** [FM-044 — Sensitive Data Exposure in API Responses](https://clrsig.com/failures/fm-044/)  

## What this failure is

The server serializes the internal `User` struct directly into the HTTP response. The struct carries fields that must never leave the server — `password_hash`, `api_key`, and `role` — but because there is no explicit response type, all fields are emitted as JSON.

The OpenAPI spec declares the `User` schema with `additionalProperties: false` and only three safe fields: `id`, `name`, `email`. Any extra field in the response violates the schema. `clrsig` catches this automatically — no hand-written assertions per field are needed.

This is the class of data leak that code review misses because the struct is "correct" and the response is "valid JSON". It only surfaces when the actual response is validated against the declared contract.

## Why clrsig catches it

The `User` schema in `openapi.yaml` uses `additionalProperties: false`:

```yaml
User:
  type: object
  required: [id, name, email]
  additionalProperties: false
  properties:
    id:
      type: integer
    name:
      type: string
    email:
      type: string
```

With `specFile:` bound in the scenario, each `type: schema` assertion validates the response body against this schema. Any field not listed under `properties` is an additional property — and `additionalProperties: false` makes that a schema violation. No per-field assertions are needed; the spec itself is the enforcement mechanism.

## Fix

```bash
go run failures/fm-044-01-sensitive-data/fixed/main.go &
clrsig run failures/fm-044-01-sensitive-data/scenarios/detect.yaml \
  --env failures/fm-044-01-sensitive-data/environments/local.yaml
# exits 0
```

**What the demo does:** introduces a `UserResponse` struct with only `id`, `name`, and `email`. The handler maps the internal `User` to `UserResponse` before writing the response. The internal struct's tags are set to `json:"-"` so it can never accidentally be serialised.

**What the production fix looks like** — always define a separate response type:

```go
// Internal model — never serialised directly
type User struct {
    ID           int
    Name         string
    Email        string
    PasswordHash string
    APIKey       string
    Role         string
}

// Response model — the only shape that leaves the service
type UserResponse struct {
    ID    int    `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email"`
}

func toUserResponse(u User) UserResponse {
    return UserResponse{ID: u.ID, Name: u.Name, Email: u.Email}
}
```

An alternative is a projection query that only selects safe columns from the database, so sensitive fields are never loaded into memory on the response path.

## Adapt this to your API

Add `additionalProperties: false` to every schema that should not leak internal fields:

```yaml
components:
  schemas:
    Customer:
      type: object
      required: [id, name, email]
      additionalProperties: false   # add this line
      properties:
        id:
          type: integer
        name:
          type: string
        email:
          type: string
```

Then run `clrsig run` with a `specFile:` binding:

```yaml
specFile: ./your-api.yaml
steps:
  - name: customer response must not include internal fields
    request:
      method: GET
      path: /customers/1
    assertions:
      - type: schema
```

If clrsig exits 1, the response contains fields that are not in the spec — investigate whether any of them are sensitive.

## In the wild

Sensitive field leaks appear when:

- **ORM auto-serialisation** — an ORM model is passed directly to the JSON serialiser; the response type and the database model are the same struct, so every column in the table becomes a JSON field
- **New column added silently** — a developer adds a `password_reset_token` column to the users table; the ORM picks it up automatically; the API response now includes it without any code change or review
- **Admin vs public API share a type** — an admin endpoint that legitimately needs `role` and `internal_notes` shares a response struct with the public API; the public endpoint leaks admin fields
- **Serialiser allow-list forgotten** — a serialiser library supports both allow-lists and block-lists; the developer adds new sensitive fields to the model but forgets to update the block-list
- **Generated code not reviewed** — an OpenAPI generator produces a client and a server stub; the server stub exposes the full model; the developer fills in the handler logic without noticing the response type includes internal fields
